# @panedesk/dsh-seat-engine

English | [中文](README.zh.md)

## Summary

Implements the [seat engine service](../../../docs/subsystems/seat.md) with a separate journal, durable queues, resource ownership, and callback outbox. Installation is explicit; ordinary profiles do not enable automatic opening.

## Use this package

External rules match `sourceId` exactly and, when present, `eventType` exactly. A configured external rule set with no match cannot fall back to project auto mode; profiles without external rules retain their existing behavior. When external rules are configured, coalescing separates external sources and event types; opening references always remain separate. Optional context references require a registered source and compatible local freezer; accepted snapshots retain text, digest, revision and task associations in the existing decision transaction before acknowledgement. Source cursors remain adapter-owned and must advance only after durable acceptance.

Mount the plugin with a complete `Config` and a `sessionLedger` provider. The ledger supplies node identity; `home` selects isolated storage. Validate positive byte, batch, deduplication, callback, and recovery limits before activation. The owner-observation interval is at most one second; observation, release, and queue-wakeup budgets together must not exceed five seconds. Missing budget or node capacity limits mean unlimited, not an invented quota.

Opt in to runtime failure supervision with `failureRecovery: { retryInitialMs: 1000 }`; omission preserves latched status and existing scheduling. The initial delay must be an integer from 1 to 300000 ms. Known transport codes (`ETIMEDOUT`, `ECONNRESET`, `ECONNREFUSED`, `EPIPE`, `node-tunnel-disconnected`, `node-deadline-exceeded`, `callback-timeout`) retry exponentially, capped at five minutes. Only a complete successful drive, including callback settlement and decision notification, clears a retryable failure. Decision listeners may receive the same committed decision again and must deduplicate effects by its identity. A failing listener does not roll back the committed decision. Listener-initiated writes return after commit without awaiting their own notification; the serialized publisher drains their decisions after the current listener settles. Concurrent callers outside that notification still await the publisher. Callback retries retain existing payloads, keys and unknown-outcome query barriers.

Every engine failure emits one safe error line through the logger and stderr, with site, code, retryability and disposition; `node.status.failure` exposes `site`, `code`, `since`, `retryable` and `attempts`, without exception text. A continuous unavailable interval emits one additional error strictly after ten minutes. State conflicts, ambiguous evidence, uncertain persistence, missing or ambiguous retention registration, owner-release budget violations and unclassified failures stop supervised driving. Later transient failures cannot clear them. Repair the underlying evidence or configuration, stop admission, drain and restart the host to replay the journal; no `engine.recover` command is currently provided. Never remove journal frames or bypass authorization to clear status. Diagnostics are runtime-only and do not alter business records; disposal cancels the watchdog.

Storage layout: the node journal keeps `owner.lock` beside `events/`. Linux and macOS retain the existing descriptor flock and immediate contention failure. Only win32 uses exclusive-share opening of this dedicated lock file, with a 100 ms retry budget and 10–40 ms backoff. Lock contents are never read or written; close or process exit releases ownership, and the file must not be removed or replaced. Startup failure diagnostics include error codes, not paths or journal contents.

Project policy defaults to `remind` with `modeChosen: false`. Each entry into approval commits one `queue/reminded` event with the pending item; coalescing, redelivery and replay do not repeat that reminder. Approval removes only reminder confirmation; capacity, time windows, exclusive resources, and budget checks still apply. Incomplete cost evidence blocks admission rather than counting as zero. The local executor owns Session effects; the engine retains original intent identities through recovery and never blindly retries uncertain model requests.

Accepted openings retain their definition, title and rendered text through queueing and recovery; current project and rule mode restrictions still apply. Manual prefill configures the original Session without sending a model request. Opening progress cannot roll back a committed budget revision. Local providers register engine-only list and close capabilities without relaxing external authority checks. Close barriers retain their operation identity, and conflicting replacement terminal summaries fail with `state-conflict` before append.

The Loader installs `subagentAdmission`, `subagentNotifications`, and `jobNotifications`. Seat-bound parents use their definition's child capacity and child-specific cache/context evidence. Completion records live under the node journal's `notifications` directory; job intent writes are synchronous before producer effects, and pending handoff/steer sends reuse stable message operations. Unsettled recovered jobs report unknown owner loss, never replay external work.

Explicit `sources` configure schedule records, registered Git paths/refs, window-ended observations, and unanswered handoff deadlines. Before enabling the `seat.open` handler, startup reconciles persisted actions with configured sources: changed records are deleted and recreated, unchanged records retain their next occurrence, and actions whose payload names a removed source are deleted even when `sources` is empty. Comparison uses normalized record fields and accounts for recurrence advancement after the last receipt. Other action names are untouched. Replacement and removal log `Seat schedule source reconciled` and `Seat schedule source removed`; failures warn through `Seat schedule registration failed` without blocking the host, leaving the handler unavailable until a successful restart. Replacement is not atomic; failure after deletion leaves the action absent until the next reconciliation. Git only reads registered repositories. Manual ingress remains with the local provider and signed external ingress with the remote provider. Source callbacks for these observers are local acknowledgements, not outbound HTTP callbacks.

Local execution policies can require a durable `recheckRequired` marker at acceptance and revalidate the original queue input before dispatch and unfinished opening recovery. Only a trusted recheck explicitly returning `retryable=false` and `effectState=none` cancels the queue entry and requires a new preflight check; retryable, unknown or unavailable permission retains the queue entry and approval state. An unchanged fixed transient class does not advance the queue revision; only an actual change in class, mode or reason advances it. Queue changes during an asynchronous check invalidate that check. Missing required policies never grant permission. Frozen chain work also rereads the execution-node definition before and after the registered policy check, at dispatch and before unfinished opening execution or recovery. A current revision differing from the retained `expectedSeatRevision` refuses execution with `revision-conflict`; revoked `remoteAdmission` permission for the retained sending node, source, principal or method refuses with `unauthorized`, both with no new Session effects. The same checks apply when source owner and execution target coincide, without refreshing frozen revisions, payload digests, operation identities or the original grant. Exact acknowledgement replay remains unchanged. These checks do not make external source reads or definition writes atomic with Session creation.

A local provider may register `preAdmit` with its engine access. Manual `openWindow`, including each opening dispatched by a local batch, awaits this hook before trigger acceptance. A refusal is returned unchanged without engine acceptance, resource or Session effects; policy audit belongs to the hook provider. Without the hook, the original admission path is unchanged.

Trusted hosts register captured identities and live policy checks through `seatAuthorizationIssuers`; callers receive instance-owned grants, not authority derived from request fields. `seatAuthorizationTransactions.transact` commits authorization and matching intent in one synchronized journal frame. Every submitted effect must carry the issued operation identity. `approve` commits the queue transition in that same frame rather than calling the legacy approval method; a denied approval keeps its original refusal on retry, so a newly authorized attempt needs a new operation identity. Revoked, foreign, stale, and mismatched grants are refused. A failed append admits no projected action; an uncertain synchronization outcome requires recovery before retry.

Authorization frames require `seat-authorization/v1`; older decoders refuse the new discriminator. Capability-aware recovery and read-only snapshots retain facts in the existing journal. New queries include `plugin`; legacy `seatAuthorizationQueries.query` skips that kind while advancing the physical cursor, never relabeling it. Queries filter by task, seat, node, kind, and time, and return the committed watermark, exclusive scan cursor, and completeness. Historical decisions without attribution remain `legacy-unknown`. Engine-effect queries and exports retain their legacy vocabulary and omit authorization facts. The independent `seatAuthorizationExports.export` service serializes a bounded `seat-authorization/v1` JSON page with its cursor, watermark and completeness, including plugin attribution; both the live engine and offline reader provide it.

Remote admission frames require `node-work-chain/v1` and a `node-route/accepted` fact beside matching issued authorization and frozen trigger intent. Replay validates the complete source identity, owner epoch, snapshot, scope reservation and original operation; a second admission for that business identity is refused before append. Legacy decoders reject the complete frame. Retained chain input separates coalescing identities and restricts every dispatch by the source mode ceiling, including after recovery. An injected routed callback sender receives the frozen owner route; only a matching committed receipt completes delivery. Missing senders and pending receipts retain retries without falling back to a same-named local source; authentication and protocol failures pause delivery. `acceptFrozen` verifies the locally issued sending-node fact and target allowlists, then commits the complete business key with authorization and frozen intent. Exact retries return the first acknowledgement before new-admission checks, even after target definitions or live issuers disappear; changed payloads conflict. Complete-process recovery rebuilds this acknowledgement from committed frames; an interrupted frame admits no partial intent. Optional `nodeWorkChainBusiness` registration waits for journal and seat admission recovery and serves exact-key queries; before recovery it reports unknown. Withdrawal rejects captured queries and frozen or batch writes, draining admitted calls before resource release; replacement cannot inherit readiness. Business registration requires both the registry and explicit `nodeWorkChain` services. Either missing dependency leaves the engine with no chain registration or chain storage and preserves ordinary replies. Frozen dispatch requires a registered permission recheck; missing execution policy retains the queue. Production outbound authorization assembly remains composition-owned. The Loader always injects a sender that selects the frozen route before resolving services. When source owner, target and callback execution node all equal this engine, it consumes only optional `seatLocalCallbackOwner`, waits for `ready` and checks current availability; a missing or withdrawn provider never falls back to a peer or source callback. Remote callbacks still resolve `nodeWorkChain` and `nodeWorkChainRouter`, obtaining fresh restricted authority through `outboxIssuer` for every query and delivery. Late installation and replacement take effect on the existing engine drive cycle. Missing services retain transient retries without creating chain storage. Before the first send, callbacks query the complete owner business key; only confirmed missing permits that send. Before dispatch the existing callback journal records `responseClass: unknown`; exceptions and timeouts query the same key during that attempt. An explicit remote pending receipt retains transient retries, and a definite remote delivery refusal with `effectState: none` retains its cause and baseline classification: authentication or protocol pauses, other refusals retry as transient. Each transient retry queries the complete key before any business send; the send-ahead unknown marker does not override an explicit owner result. Issuer withdrawal does not clear uncertainty. Unknown retries perform only exact queries, never business replay, even when the owner reports missing. Unknown remains visible in the callback projection and `engine.operation` as pending progress blocked by `callback-outcome-unknown`; only an exact settled owner result resolves it. Pending receipts, unavailable authority and disconnection retain the existing exponential retry schedule; only owner `committed` completes delivery. The original route, callback identifier, payload digest and model evidence never change.

`queryRoutedCallback(engine: SeatEngine, request: NodeWorkChainOperationRequest): Promise<DeliverSourceCallbackRequest | undefined>` waits for journal recovery and returns a detached persisted callback, route and model-evidence body only when every complete-key component and `payloadDigest` match. The sending node is this engine, the principal is retained from its accepted route, and the operation is the route's original operation. The lookup performs no writes and returns no reusable authority. Restricted issuers must also compare the supplied request body and destination with the retained body before issuing authority. Missing matches confer no permission. Without explicit chain assembly, the local callback path and storage remain unchanged.

`registerSourceProxy` installs one in-process source composition for remote trigger acceptance and context opening or wake. `target` selects ownership without reserving work; `prepare` supplies the source owner's durable frozen snapshot, reservation and original local-action grant. The engine verifies that grant and persists the complete local input, frozen payload, business key and original attribution in required `node-source/updated` frames before calling `send`. The engine never receives an issuer. Composition persists its outbox intent, signs fresh exact-payload authority and invokes the node-link router with the matching delegation. Confirmed results are retained; unknown transport or result persistence retains the original reservation without local queue or resource allocation. Exact retries return the durable result, or use optional composition-owned `reconcile` for an unknown intent; absence never blindly resends. Disposal rejects new sends and drains admitted work. Without registration, the original local path and remote refusal remain unchanged.

Trusted wake selection and missing-window frozen opening share the local opening admission slot. Pending or unfinished openings prevent another fallback for the same seat. Existing-window wakes persist the original receiving grant and deterministic delivery action together in private `node-wake/updated` frames, not trigger effects; legacy readers reject this discriminator. Persistent message delivery reuses the wire-operation/window identity after recovery, and the first receipt is immutable. Exact retries retain their original result; changed inputs conflict and revoked grants cannot admit new deliveries. Recovery completes retained intents before chain queries become ready. Multiple-window selection and stored-budget-stopped replies remain local wake semantics.

Node batches retain independent member decisions. Each `node-batch/accepted` fact requires `node-work-chain/v1` and binds the original batch payload and issued authorization to one deterministic member action in the same frame. Recovery rejects mismatched bindings and returns the first queued acknowledgement; interrupted later members do not roll back committed earlier members. No new local grant is issued.

Failed routed attempts persist optional outer `lastDiagnostic` beside the attempted delivery in the same journal commit, without changing callback bodies or business digests. The eight stages are `retained`, `issuer`, `local-query`, `local-dispatch`, `peer-query`, `peer-dispatch`, `owner-inbox` and `writeback`. Cause identifiers match `[A-Za-z0-9][A-Za-z0-9._/-]{0,127}`; reasons are nonempty, at most 512 UTF-8 bytes and contain no control characters. Exception text is never copied. Complete decision frames remain subject to `maxDecisionBytes`, without truncation; failed uncertainty writes prevent dispatch and failed diagnostic writes cannot clear retained unknown. Success removes only the latest diagnostic, preserving historical attempts; older records gain no default field. Existing `engine.query` filters callback effects by nested seat, related tasks and primary task, retaining bounded pagination and authorization. Operation identity conflicts pause rather than retry. Local operators resolve paused callbacks through `engine.callbackResolve`. Optional observations alone do not justify deployment downgrade: retained new-method evidence still requires compatible readers.

Routed callbacks freeze execution-node model evidence before their first durable publication. The registered local executor supplies a recorded model or explicit missing evidence; missing evidence never falls back to seat configuration. Replays retain the original evidence and digest, including missing observations. Journal admission rejects inconsistent callback digests, execution identities and attempts to replace already frozen evidence.

`seatAuthorizationTransactions.operation` rebuilds approval registration and correlated opening progress from the committed queue and trigger facts. Pending reasons, created phases, cancellations and recorded failures remain queryable after restart without executing work or exposing frozen instructions. Approval does not imply creation or first-turn success.

Authorized `cancel` commits `queue/cancelled` with its issued authorization, principal, kind, operation ID, queue ID, timestamp, revision and optional reason. Reasons contain at most 512 UTF-8 bytes and no control characters. Operation lookup returns the settled cancellation receipt; redacted effects retain only reason presence. Queue and operation indexes retain the latest 256 receipts each, with older lookups reconstructed from committed decisions. Pending and approved-but-undispatched items have no budget or resource reservation: cancellation neither creates nor changes those projections. Dispatched, opened and unknown targets retain `revision-conflict` with a structured `cause.reasonCode`; unaudited cancellation retains its original bytes and attribution. Cancellation itself does not directly release external reservations. For a complete frozen chain, pre-open automatic refusal, retention expiry and both manual cancellation entry points append one unique `rejected` callback for each originally accepted item in the same transaction. The original route, source and operation identity remain unchanged; manual cancellation callbacks use a fixed safe reason without free-form audit text. Reservations may be released only after authenticated receipt by the original owner; offline, unknown or paused delivery does not imply release. Callback construction failure, write failure or a complete frame exceeding its limit must not remove only the queue entry.

Directory synchronization tolerates only `EPERM`, `EISDIR` and `EINVAL` from opening or flushing directory handles on Windows. File writes, file synchronization, directory close failures and every non-Windows failure still propagate; Windows does not gain a guarantee that unsupported directory metadata synchronization completed.

Committed decisions update projections and outbox delivery. Source callbacks are at-least-once with stable identities; credentials are supplied by source registrations rather than stored in engine records. Disposal stops ingress, drains owned work, flushes the journal, and releases writer ownership.

### Callback parking and operator resolution

Local source exceptions use `lastDiagnostic.stage=local-dispatch` and fixed `cause.code` values: `callback-unclassified-error`, `callback-timeout`, `callback-authentication-failed`, or `callback-protocol-error`. Exception messages, stacks and nested causes are not stored. Unclassified errors and timeouts conservatively report unknown effects. Correlation uses the retained route operation, otherwise the opening operation, otherwise `callback/` followed by the SHA-256 digest of the canonical callback ID, including callbacks without a session.

Each continuous transient segment has a built-in 900000 ms wall-clock limit starting at the first committed `callback/attempted.observedAt`. Restart, offline time and changed transient detail codes do not reset it. Success, authentication, protocol and completed unknown outcomes end the segment; unincremented send-ahead unknown barriers neither start nor end it. Checks run before `nextDue` and external I/O, and again after completion. Success wins over expiry. Before I/O, parking appends one attempted transition with unchanged attempt; after an actual call, its single attempted frame increments attempt and records parking without a second transition. Both use `phase=paused` and `nextDue=null`; subsequent drives and restart append no frames for that callback while it remains parked. This is independent of retry-backoff configuration and pre-open retention registration.

Remote transport-none, unavailable-link and missing-hello-capability failures park with `callback-link-unreachable-limit`; other failures use `callback-transient-limit-reached`. An authenticated hello observation from the existing cached router status resumes a link-class callback once with `callback-auto-resumed-on-link-ready` only when its `observedAt` is strictly later than the latest parking frame. A later parking requires a newer observation; the old cached hello cannot resume it. The owner must be connected, reachable and advertise `node-work-chain/v1`; failed or repeated hello observations create no extra resume frames. The resumed segment starts at that transition, and delivery still rechecks current routing authority. Other-class parking requires an operator.

`engine.callbackResolve({ callbackId, action: 'resume' | 'abandon', expectedAttempt })` requires a live local-operator grant. Resume retains all identities and payloads, writes `callback-manually-resumed`, and starts a new segment. Abandon writes `callback-manually-abandoned` and the terminal phase `abandoned`, without claiming an owner business effect. An executed action with the same callback ID, action and expected attempt replays current state without a frame only if no later parking frame exists. Otherwise non-paused state refuses before attempt comparison; a newly parked callback can be resolved again at an unchanged attempt. Unknown callbacks, non-paused callbacks and attempt conflicts refuse without a frame. Ordering is per `(sourceId, sessionId, triggerId)`: paused opened blocks ended; resume waits for opened delivery, while abandon permits ended on the next drive. See the [authenticated command-line example](../../host/host-admin/README.md#callback-resolution).

### Pre-open terminal outcomes and transient retention limit

Before external admission, composition must register every trusted route on the actual executor instance with `SeatEngine.registerPreopenRetention({ sourceId, sourceOwnerNodeId, limitMs, projectId? }): () => Promise<void>` and retain each disposer through a lifecycle effect. The optional `projectId` restricts registration to that project; omitting it covers all projects on the frozen `(sourceId, sourceOwnerNodeId)` route. A unique exact project match takes precedence over a unique route-wide match. Multiple matches at either level, or no match at either level, use the built-in 900000 ms fallback limit, equal to the composition default. Until expiry, these items remain queued with `provider-unavailable`, cannot open, and retain fixed safe and engine-failure diagnostics; authorized manual cancellation remains available. At expiry they use the same terminal cancellation and owner callback as registered routes. Public-only deployments can use `registerPreopenRetention` to set another limit; no new public configuration key is required. Identifiers use the seat service's branded types, and registered limits are positive integer milliseconds from resolved configuration. Withdrawal of the recheck provider does not withdraw the limit; composition disposal immediately removes the registration and waits for the current drive cycle to finish. Compositions with limits above the fallback must keep their registrations continuously installed: during a hot-reload withdrawal gap, older items already beyond 900000 ms can terminate under the fallback.

Timing starts at `observedAt` in the first committed frame for the current fixed transient class. Approval, same-class retries, coalescing and restart do not reset it; an actual class change starts a new interval. Legacy items start timing only when a fixed class is first written, without backdating. A backward wall-clock adjustment does not reset the start. An independent check runs before the executor and external reads; the first drive cycle at the limit cancels and notifies in the same frame with `gate-denied`, `retryable=false` and `effectState=none`. A missing provider or executor cannot bypass this check. Ordinary pending approval, closed mode, budget and capacity waits, and already dispatched work do not use this terminal path.

Original source-operation queries and all three exact frozen business queries return `rejected` and its reason within the existing `settled` result when a pre-open terminal outcome is proven; that outcome takes precedence over unknown callback transport outcomes. Repeated writes still return the first acceptance receipt. Exact queries validate the complete key and digest first, and the current pending revision is the actual queue revision. The cancellation operation identity still returns the original audit receipt; the generic terminal result gains no revision field.

Before publishing readiness, startup builds a temporary index from the complete history and appends one unique callback frame for each proven frozen terminal outcome with no execution or callback facts, with `causedBy` referencing the original cancellation event. The four terminal classes are automatic refusal, definite capacity-admission refusal, authorized manual cancellation and legacy unauthenticated frozen cancellation. Original frames remain unchanged, queues are not revived, and automatic reasons retain their original `retryable` value. Ambiguous evidence prevents reconciliation and produces a safe diagnostic; append failure prevents startup completion. Any historical callback resumes delivery through the existing outbox without creating another callback.

### Upgrade and rollback

The source owner and executor must use versions validated as a pair and the same composition-provided limit. First stop new source admission, back up all persistent domains and watermarks on both sides, restore the owner before starting the executor, and verify the original identities, epochs, authorization and capabilities before normal reconciliation. Resume new work only after callbacks settle. No persistent fields, public configuration keys, wire methods or capability bits are added. Compatible readers can understand the existing frame structures, but older implementations may still cancel incorrectly or omit callbacks; readability does not authorize an operational rollback. While queues are active or callbacks remain unsettled, preserve the complete new ledger and repair by rolling forward. Do not delete appended frames or restore an old backup on only one side; minimum reader-version restrictions for retained new-method evidence still apply.

## Model Experience

### Executor-owned work

#### What the model sees

The `seatEngine` provider contributes no tool schema or prompt. Registered executors deliver opening and budget notices through the existing message services.

#### Token effect

Admission and queries use no model tokens. Admitted work and cache maintenance can issue model requests through their respective providers; accounting includes descendants and maintenance.

#### KV Cache effect

Queries and journal commits preserve existing request prefixes. Cache maintenance is an independent provider request; unknown renewal outcomes are retained rather than replayed automatically.

## Known Limitations and Deferred Work

- Failure supervision parks automatic driving and decision notification, not all inbound writes. Admission, transactions, policy and budget updates, child lifecycle, manual renewal/replacement, close recording and authorized callback resolution retain their existing checks and may still commit or perform their existing effects. Operators must stop admission separately before repair; unavailable status is not a global write fence. Unrecoverable supervision also pauses automatic pre-open expiry and callback reconciliation until restart after repair.
- `seatAuthorizedEngineActions` commits renewal attempts and replacement queues with issued grants, preserving legacy methods when no grant is supplied. Current authority is rechecked before admission; historical receipts cannot dispatch another action. Issuer registration alone does not wire CLI or all automatic ingress; those consumers still need explicit adapters.
- Opening and recovery require a registered local executor; absent evidence leaves work pending instead of fabricating a window.
- The active provider owns a writer and reconciliation timer; it is not an offline read-only query provider.
- Account concurrency statistics are diagnostic, not an enforced account limiter.
- M8b: abandoning a routed callback does not modify `chain-sent`; transport recovery can still reconcile the original owner key. A late owner `committed` receipt does not itself clear seat budget parking: other-class parking still requires operator resolution, while link-class parking requires a newer ready hello. These independent states do not imply owner `paused`. Abandon is not an owner terminal receipt. Unknown callbacks and adapters that never settle are outside the transient time limit. Readers predating `abandoned` cannot replay that phase; retain the complete journal and roll forward rather than deleting transitions.
