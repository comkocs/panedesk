# 开局向导(搭建工作流)

[English](getting-started.md) | 中文

在宿主应用中可调用内置 `workflow-pack` 技能读取本向导；调用本身不授权写项目文件。需要 Python 3.11 或更新版本，不用安装其他软件包。下面命令均在拷来的通用包文件夹内运行；项目根指新项目放主要文件的文件夹。

## ⓪ 先分流

本件只管新项目从零搭起；项目已在运转、有自己的规矩与文件的老项目，转读同包《workflow-checkup.md》做体检，不走本件。

新项目先按三级找产品文档：① 决策者给的、或项目根 `需求/` 下的产品文档（任何格式）直接用；② 没有就只读扫项目目录（含子目录），找名称或内容像产品 / 需求 / 研发 / PRD / 原型的件，找到后问决策者一句「按它来？」，点头才采用；③ 仍没有就简单问三句：做什么、给谁用、第一版要有什么。决策者想把需求先成套核对时，提一句可选的《requirements-review.md》（任意聊天窗都能做），不在本窗走整套核对。

## ① 先记原话

把决策者第一句需求逐字追加到项目根的 `资料/决策者原话.md`，带上从当前系统取得的日期与时刻。以后补充也只追加，不覆盖，不把自己的理解混进原话。先不改规矩，也不开始制作成品。

## ② 一次核对需求

⓪ 找到了产品文档的，十题由你从文档直接归纳填好，不逐题问决策者；只把文档没写到、又影响判档的项一次问完。没有文档的，已说清的直接复述，不重复问；其余一次问完下面十题。每题都给推荐，决策者说按推荐就照推荐；没问到的照缺省先做后报。不要把猜测冒充原话。

| 题 | 用人话问 | 推荐缺省 | 决定需求卡字段 |
| --- | --- | --- | --- |
| 1 | 这次做什么、给谁、对方最终拿到什么？你最在意什么、有什么绝不能做？ | 从原话拟项目名和一句话；未说明时先做给用户看的最小可用成果，先保正确与可修改；不清楚的限制列为自主假设，不编成决定。 | `[项目] 名、一句、受众、成品`；取向摘要写入“一句”，原话与限制完整留在原话记录。 |
| 2 | 准备同时开几个主要工作窗口？ | 1 个；窗口指同时在跑的主要对话，不把临时助手计成主窗。 | `[规模] 同时窗数` |
| 3 | 准备分几个长期职责，例如写作与校对？ | 原话里点到几块分工就记几个；两三个窗口时按是否各管一块长期职责来定，不按窗数推；没说明长期职责时先按 1 个，同时窗数至少 4 个且没点到分工的按窗数的一半向下取整；不把决策者算进去。这个数会影响规模判法。 | `[规模] 分工位数` |
| 4 | 要分别管理几套代码或资料仓？ | 普通创作填 0，软件项目填 1；文件夹多不等于多套仓。 | `[规模] 仓数` |
| 5 | 要写程序、检查程序能否运行吗？ | 普通创作否，软件项目是。 | `[特征] 代码` |
| 6 | 要部署产品、供在线用户使用或持续运营吗？ | 普通创作否，准备部署并维护在线产品的软件是；只发布文章、成片或维护公开代码仓不算上线。 | `[特征] 上线` |
| 7 | 会批量制作图片、声音、视频等素材文件吗？ | 短视频是，纯文字写作和普通软件否。 | `[特征] 素材` |
| 8 | 有没有必须只认一份准数的规则或数值，例如收费标准？ | 否；有这类业务要求才开。 | `[特征] 数值` |
| 9 | 会把任务分给多家不同模型的助手吗？要设独立只读的审查岗位吗？要把规矩与原话放进结构化库并每日导出吗？ | 三项缺省都为否；只是多开同一种助手不算多模型；大型研发预设的审查岗、规矩库为是。 | `[特征] 多模型、审查岗、规矩库` |
| 10 | 你、总协调、项目依据与工作记录分别叫什么、放在哪里？ | 决策者、总协调；依据用所选预设的叫法，工作记录用一个记录文件；其余沿用预设。同时 ≥4 窗、或预计同时在办 ≥10 件任务、或周期 ≥1 个月时，工作记录推荐用工单类工具，不用单个记录文件。 | `[称呼]`；项目名、受众、成品缺省取 `[项目]` 的对应值。 |

确认后在原话记录末追加“需求核对结果”和“自主假设”，明确两者不是决策者原话。取向或限制不能塞入一句话的，仍完整记录在原话件。

把决策者原话里本项目独有的要求逐条摘进项目根的手写件 `本项目自定.md`，每条一行，格式为「要求 —— 出处:资料/决策者原话.md 第 N 条」；不编、不扩写。与通用条冲突时以本件为准；要压某条通用条的，在该条后写「压 G-xxxx」，并在③制作的 `requirements.toml` `[手调] 减` 里同时减掉那条，理由写「本项目自定压掉」。

## ③ 从最近的预设做需求卡

先看有哪些预设：

```text
python3 -X utf8 tools/trim.py profiles
```

从 `profiles/` 拷最接近的一份到包根，命名为 `requirements.toml`。按核对结果改值；保留中文节名、键名两侧的引号，例如 `["项目"]` 和 `"名"`，这是 TOML 格式的要求；保留七个特征的 `true` 或 `false` 写法。小说选 `novel-writing.toml`，短视频选 `short-video.toml`；写程序的项目二十万行以内选 `medium-software.toml`，超过二十万行或多分工持续研发选 `large-research.toml`，决策者点名「一窗到底」才选 `small-software.toml`。

推荐把 `[规模] 档` 改成空字符串 `""`，让工具按大、中、小顺序判断：同时窗 ≥7，或分工位 ≥6，或「仓 ≥2 且上线 且分工位 ≥4」为大；否则，同时窗 4~6，或分工位 2~5，或「仓 ≥2 且上线」，或写程序为中；其余为小。仓可以是代码仓或办公资料仓，1 窗、1 分工、2 仓且上线为中。小说预设为 2 窗 1 位、短视频预设为 3 窗 1 位，均为小。明确填写档时，以档为准；与数字不一致会提醒一句。

写程序的项目至少中档：预计代码不超过二十万行的，用中型软件预设，缺省只开两窗——总协调管规划与需求核对，技术主窗一位包全部技术（G-0222）；预计超过二十万行的，明写 `"档" = "大"` 并按模块增设位主；决策者点名「一窗到底」时才明写 `"档" = "小"`。

`[称呼]` 可填：项目名、决策者、总协调、受众、成品、真源件、留痕处、口径件、规矩总件、作业件、接管件。不填或填空沿用缺省；项目名、受众、成品先取 `[项目]`，其余依次为决策者、总协调、项目真源.md、记录.md、当日口径.md、宪法.md、作业规矩.md、接棒记录.md。称呼只是正文叫法，不改工具固定输出的文件名；指向其他名字时要明确它和实际文件的对应。

`[手调] 加`、`减` 缺省都为空列表。确需单独保留或拆掉某条时，按 [条目表](entries.zh.md) 的编号填写，每一项都必须有理由。先执行加，再执行减；同一编号两边都有时，以减为准。下面只是填写形式，编号要换成表里实际存在的编号：

```toml
["手调"]
"加" = [{"编号" = "G-0001", "理由" = "此项工作现在已经需要。"}]
"减" = []
```

## ④ 校验并裁剪

```text
python3 -X utf8 tools/trim.py validate
python3 -X utf8 tools/trim.py generate --card requirements.toml --out pending
```

旧中文命令 `出`、`校验`、`表`、`档案` 和参数 `--条目`、`--卡`、`--出` 保持兼容。工具缺省读包根的 `entries.jsonl`；验证其他条目表可加 `--entries file.jsonl`。`table --entries file.jsonl` 会在该条目表旁生成 [条目表](entries.zh.md)，供人阅读。

若校验或依赖报错就停止，把报错涉及的编号和原因说明白，再改需求卡或条目表重裁；不能暗中补依赖。每条保留规则都附“为什么”。有保留条文使用口径件时，才生成空的 `当日口径.md`；没有就不生成。

输出目录没有 `本项目自定.md` 时，工具另写 `本项目自定_样板.md` 供手写时参考；已有本件时不写样板，工具从不生成、挪动或覆盖手写件。

## ⑤ 给决策者看瘦身结果

读 `pending/裁剪记录.json` 和 `pending/拆掉清单.md`，用几句人话说明：本次规模与特征是什么，留了哪些模块、拆了哪些、各在什么情况下加回，还有哪些自主假设。全拆模块在清单里只占一行，显示条数和最常见的加回条件；部分拆掉的模块每条一行。完整理由见 [条目表](entries.zh.md)，逐条拆因与加回条件仍在 `裁剪记录.json`。涉及条目时附编号，供查对，不让决策者读代码。

第一窗可按这一类项目当下的通行做法，提出最多 5 条「建议写进本项目自定」的要求。每条都标「建议(非原话)」，并用一句话说明为什么；例如历史类标史料出处、记账类保护数据隐私与备份、企业平台做租户隔离。建议不是决策者原话，先只放在下面的报告里，不直接写入 `本项目自定.md`。决策者逐条点头后，才由第一窗手写追加到项目根的 `本项目自定.md`，每条出处写「决策者 <时刻> 同意第一窗建议」，其中时刻从当前系统取得；不点头的不写。若压通用条，同②同步更新需求卡的 `[手调] 减`。

按下面模板把判定一次报告给全，等决策者点头或修改；说“按推荐”即照推荐。修改裁剪则回到需求卡重裁，不直接改生成件。

### 给决策者的话

```text
本次规模与特征：……
留下：……
拆掉与加回时机：……
预设与岗位：……（写程序的项目缺省两窗：总协调 + 技术主窗）
工期：……（AI 工时，人类工时 ÷ 15；例：150 天 → 10 天）
自主假设：……

建议写进本项目自定（最多 5 条，无建议写“无”）：
1. 建议(非原话)：……；为什么：……
请逐条确认是否同意；点头的才写入本项目自定.md，出处记“决策者 <时刻> 同意第一窗建议”，不点头的不写。

现在落地还是先停？
```

写程序的项目点头后，另按功能切片拆出首批单：一单从数据、逻辑、界面到测试一口气交付，每单写单名、依赖和一句验收「使用者打开能看见什么」，记进工作记录（G-0223）；派单前先问一句一个人做不做得完，做得完就一单到底。

## ⑥ 放到项目根并写明开窗顺序

确认后，把需求卡保存到项目根，把 `pending/` 中的生成件放到项目根。若包根不是项目根，保留整包作为以后重裁的工具与条目来源。项目根若已有同名生成件，先挪入 `_旧版/` 下的新子目录，不覆盖、不删除；不要把整包的说明文件或资料随意搬走，也不要挪动或覆盖项目根的 `本项目自定.md`。

每个新窗口先读项目根的 `开窗必读.md`，再依次读 `本项目自定.md`（如有）、`宪法.md`、`作业规矩.md`；需要具体操作时读 `做法建议.md`。本次有 `当日口径.md` 才读它。

为让新窗口自动照做，在项目根写 `CLAUDE.md`（Claude Code 与编辑器里的 Claude 窗每次自动读）与内容相同的 `AGENTS.md`（其他编程助手读），只写三行：对决策者一律用中文人话；每个新窗口先读 `开窗必读.md` 并照它的顺序读；压缩上下文时摘要必须保留决策者的决定（带时刻）、跨窗约定的数值与时段、在跑助手及其在等什么。已有同名件只在末尾追加这三行，不覆盖原内容；这两件只放入口与压缩提示，不写成第二份规矩。`拆掉清单.md` 说明为什么拆和什么时候加回，`裁剪记录.json` 留下编号与原始输入的摘要，便于确认用的是哪版。

## ⑦ 随项目生长而加回

定期看 `拆掉清单.md` 的加回时机或条件；全拆模块的一行只列最常见条件，逐条条件查 `裁剪记录.json` 或 [条目表](entries.zh.md)，不另编一套门槛。出现条件写明的数字或工作变化就核对需求卡：例如同时窗数达到 4 或 7、分工数达到 2 或 6；开始维护多仓且上线、或开始写程序时进入中档，另有至少 4 个分工位时进入大档；开始写程序、上线运营、批量产素材、维护统一数值、派多家模型、设审查岗、建规矩库。具体是否要加回，以对应条目的条件为准。

更新数字、档和特征后，重新执行校验与裁剪，再把“这次加回什么、为什么”给决策者看；确实只需单条才用带理由的手调加。项目缩小时也重新核对，别让旧的大套规矩一直压着小项目。

决策者新提的长期要求，照②的格式与原话出处追加进 `本项目自定.md`；要压通用条时同步更新需求卡的 `[手调] 减`。

重裁到同一目录时，工具会先把已有生成件挪到该目录的 `_旧版/第若干次/`，再写新件；不删旧件，也不移动其他手写资料。若先裁在待确认目录，再往项目根放，项目根旧件也必须先挪 `_旧版/`。把变更原因与新时刻追加到工作记录，保留旧需求卡和原话，不把历史改成新说法。
