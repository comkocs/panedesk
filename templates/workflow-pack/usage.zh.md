# 使用方法

[English](usage.md) | 中文

## 这包是什么

这是一套能带去新项目的 AI 合作规矩和一个小工具,共 225 条可选规矩,分 16 个模块(底线、决策与原话、真源与完成、分工与权责……一直到审查席、真源库)。你不必一开始就全用,也不必自己逐条删:先把项目说清楚,让第一个 AI 窗按项目大小和工作类型选出够用的一套。

它和「只有流程」的通用包差在两处:

- **每条规矩都带「为什么」**:写清它防的是什么真出过的问题、当初决策者是什么意思,不是一句空口令。
- **按项目瘦身**:暂时用不上的规矩会拆掉,并写明将来什么情况该加回。写小说不用背软件研发的整套,一个人的短视频账号也不用设审查岗位。

## 三个入口,选一个

- **核对产品需求**:还没有产品文档的新项目,先把产品想清楚再动手(可选,任何聊天窗都能做)。开窗词:**「/workflow-pack 请读通用包里的《requirements-review.zh.md》,帮我设计产品研发文档,多轮改到定稿。」**
- **搭建工作流**:已有产品文档或刚核对完需求,要能跑命令的编程窗。开窗词:**「/workflow-pack 你是本项目第一窗,先读通用包里的《getting-started.zh.md》,照它搭建工作流再开工。」**
- **优化工作流**:已有老项目,给工作流做一次体检。开窗词:**「/workflow-pack 请读通用包里的《workflow-checkup.zh.md》,给这个项目做一次工作流体检。」**

## 新项目怎么起

1. 把整个文件夹拷到新项目里,别只拷一份规矩。小工具要 Python 3.11 或更新版本,不用另装软件包;你不会运行也没关系,AI 窗会照说明操作。
2. 打开第一个 AI 窗,说上面「搭建工作流」那句开窗词,接着说你想做什么。
3. 它先找产品文档:你给的、或项目 `需求/` 下的直接用;没有就只读扫项目目录找像产品 / 需求 / 研发 / PRD / 原型的件;再没有就问你三句(做什么、给谁用、第一版要有什么)。想把需求先成套核对的走《requirements-review.md》。有文档时十题由它从文档直接归纳,只补问文档没写到、又影响判档的少数几题;不确定就说「按推荐」。
4. 它做出项目自己的 `requirements.toml`,选出适用的规矩,把「留了什么 / 拆了什么 / 什么时候该加回 / 用什么预设 / 开几个窗 / 工期多少(AI 工时,按传统人类工时 ÷ 15,例:150 天 → 10 天)/ 自主假设」合成一次判定报告给你点头。写程序的项目缺省只开两窗:总协调 + 技术主窗。它还可以提最多 5 条「建议的本项目要求」,**你点头的才写进去**;点头后写程序的项目还会按功能切出第一批单,每单一句验收「使用者打开能看见什么」。
5. 确认后,生成的规矩放进项目主文件夹。以后每个窗口先看 `开窗必读.md`,再按它指的顺序读规矩;不要只靠 AI 的记忆。第一窗还会在项目根写一份三行的 `CLAUDE.md`(和同样内容的 `AGENTS.md`),以后在 VS Code 或 Claude Code 里开新窗,它会自动先读入口,你不用每次提醒。

本项目独有的要求(比如写小说的「前面写过的设定别前后矛盾」)手写在项目根的 `本项目自定.md`,每条带你原话的出处;和通用规矩冲突时以它为准。裁剪工具从不生成、挪动或覆盖这个件,重新生成规矩也冲不掉它。

## 不同项目会留下多少

我们拿四个模拟新项目试过(第一窗按开局向导走完,再由另一个 AI 站在项目主人角度挑毛病,改了两轮,又经一道独立审计);下表为包源报告的当前版本重裁结果，不是本次宿主应用会话的实测,审查岗与规矩库均关闭:

| 项目 | 判的大小 | 留下 | 宪法 + 作业规矩(UTF-8 字节) |
| --- | --- | ---: | ---: |
| 一个人写 60 万字网络小说,一两个窗口 | 小 | 29 条 | 10,948 B |
| 一个人做历史冷知识短视频账号,两三个窗口 | 小 | 33 条 | 12,688 B |
| 一个人做手机记账 App,三四个窗口分前端、后端、测试 | 中 | 105 条 | 34,262 B |
| 十个窗口、三个代码仓的在线协作平台 | 大 | 196 条 | 64,871 B |
| 两个窗口、一套代码仓的上线小软件 | 中 | 105 条 | 34,001 B |

最后一行演示判档新法:窗口再少,只要写程序并上线就按中档起步,写程序那套规矩一次到位。

大型研发全开时 225 条全留,就是我们自己这套模式的通用版。

## 项目变大了怎么办

窗口或分工变多,或开始写程序、上线运营、批量做素材时,让 AI 看 `拆掉清单.md`。它按拆的原因分组,比如「项目长到中档时加回」「开始写程序时加回」,每组一行列出那些规矩;每条的详细加回条件在 [条目表](entries.zh.md)。条件到了,就改需求卡重新生成,不在旧规矩上随手补字。单独加减一条也可以,但必须写明理由;要是拆掉了另一条依赖的规矩,工具会报错,不会偷偷替你补回。

重新生成时,旧的生成件自动挪进 `_旧版/`,不删除;原需求卡和改动原因也留着,日后查得清当时为什么这样选。项目缩小了也一样重裁,别让大项目的整套一直压着小项目。

## 五份现成起点,选最像自己的

| 预设 | 适合什么项目 |
| --- | --- |
| large-research.toml | 很多窗口和分工长期协作,程序、上线、素材、数值、多家模型都可能有。 |
| medium-software.toml | 一位总协调加一位技术主窗做软件(二十万行以内),准备上线并维护。 |
| small-software.toml | 一个窗口一口气做小工具或原型,还不维护在线产品;决策者点名「一窗到底」时才用。 |
| novel-writing.toml | 以设定集与大纲为依据,持续交给读者的连载章节。 |
| short-video.toml | 按选题库与脚本做素材,交给观众的成片。 |

预设只是起点,不是贴死的标签。大小这样判(从大往小看):同时窗 ≥7,或分工位 ≥6,或「仓 ≥2 且上线 且分工位 ≥4」= 大;否则,同时窗 4~6,或分工位 2~5,或「仓 ≥2 且上线」,或写程序 = 中;其余 = 小。预计要写程序的项目至少中档。仓可以是代码仓或办公资料仓;只发布文章、成片或维护公开代码仓不算上线。照真实情况改需求卡;拿不准就让 AI 先说推荐理由,你再定。

审查席、真源库不随大档自动开启:需求卡另有「审查岗」「规矩库」两个特征,分别表示设独立只读的审查岗位、规矩与原话进结构化库并每日导出,缺省都为否;大型研发预设两项为是,其余预设为否。
